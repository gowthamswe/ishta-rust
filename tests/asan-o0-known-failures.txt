# Every entry names the bug row that owns it. Nothing goes on this list without

# silenced.

# THE LIST ONLY SHRINKS. scripts/asan-o0-leg.sh fails both when an unlisted
# fixture starts failing (a regression) and when a listed one starts PASSING

#
# These are NOT -O0-only curiosities dismissible as debug-build noise. At -O0 no
# pass pipeline runs, so the allocations the fixture intends actually happen;

# just deletes the evidence along with the allocation.
#

# B-2026-08-05-7's tensor entry (asan_tensor_lifecycle_clean) was REMOVED
# 2026-08-06: the fresh-temp owned-argument leak it named is fixed. Owned tensor
# params are caller-retains like Vec/String, and the caller-side materialization
# that covers those is gated on the Vec `{ptr,len,cap}` LLVM shape, which a
# tensor — a bare `ptr` to one `[rank][dims][data]` block — is not. It now gets
# its own caller-scope `FreeTensor` behind the same passthrough guard.
#
# Not an -O0 curiosity either: with a callee that reads the WHOLE block
# (`t.sum()` rather than `t[0, 0]`) the leak measures 2,240 B / 40 blocks
# IDENTICALLY at -O0 and at the default -O2. The fixture read it one element at
# a time, which is what let LLVM delete the allocation and made it look
# -O0-only. `asan_tensor_fresh_temp_owned_arg_no_leak` carries the summing form
# so the default leg gates it too.

# (asan_struct_field_boxed_heapless_option_envelope_owned) was REMOVED

#   * the consuming arm, which takes it over from the scrutinee — the arm's

# B-2026-08-12-19's entry (asan_struct_field_boxed_interior_nonbinding_callee)

# fixed and the ratchet's "a listed fixture that starts PASSING fails the leg
# too" direction is what flagged the line as stale.
#
# The entry copy of a `Result[S, i64]` param whose struct payload has a boxed

# assumed: the fixture's program reports 168 allocations for 40 iterations, four

# B-2026-09-07-20's entry
# (asan_stored_argument_is_owned_by_its_new_home_not_the_caller) was REMOVED

# It was found by running this leg for the first time since `d971ad5`

# Worth recording: the 35 B was TWO UNRELATED DEFECTS sharing one fixture, and
# the summary line hid that — three allocations, all attributed to `mk`, which
# reads like one leak with one cause. Reduced cell by cell under valgrind they
# split 19 / 16 across two cells with nothing in common but the struct type:
#
#   * the `k` cell (19 B) — a CONDITIONAL store whose non-storing path had no
#     owner. B-2026-08-30-28 registers such a param BODIES ONLY on the premise
#     that "the caller still owns the memory", which is false for a param the
#     prologue REFUSED to own: it is forwarded, and the caller stands all the
#     way down. The `Drop` body ran while the whole of the struct's heap
#     leaked, which is the signature of that premise failing. The conditional
#     -RETURN sibling had already been corrected the same way (B-2026-09-06-69);
#     this is the STORE escape route, one over.
#   * the `b` cell (16 B) — a field ASSIGN displacing a struct that owns a
#     `shared` field. `emit_struct_drop_synthesis` skips shared fields by
#     design, because a live binding releases through a separate scope-exit
#     channel; a DISPLACED value has no such channel.
#
# The second root has an INDEX-assign twin (`v[0] = mk(38)`) that leaks at the
# DEFAULT -O2 as well, since the element stays reachable through the container
# and LLVM has no dead allocation to elide. It is fixed with the same helper and
# pinned in `asan_conditionally_unstored_and_displaced_struct_values_have_an_owner`,
# which is what gives this family a gate on the leg CI actually runs — every
# other cell of it is -O0-only.
#
# The reduction is the lesson: an -O0 summary line names allocation SITES, not
# causes, and `mk` was the allocation site of both. Splitting by CELL before
# reading any codegen is what separated them.
