# failing (a regression) and when a listed one starts PASSING (the owning bug

# the allocator gate with real (unoptimized-away) allocations, this one adds
# ASAN's memory-ACCESS checking on top. Its failure set is therefore a superset,
# and merging the two would let an access-class regression hide behind an
# allocator-class quarantine entry that happens to name the same fixture.
#

# local SHA is rewritten by the pre-push rebase, so the public base is cited

# B-2026-09-07-54 REMOVED 2026-09-08, its owning row fixed. The entry read:
#
#   `__karac_vec_elem_rc_dec_Node` reads offset 0 of a 32-byte block that
#   `__karac_rc_drop_Node` already freed. No double free, no leak.
#   memory_sanitizer_tests::asan_let_bound_vec_option_shared_reused_no_uaf
#
# The cause was an untyped `let s = <receiver>.clone()` yielding
# `Option[shared T]`, which no case in stmts.rs's untyped-let chain registered
# into the caller-retains model: each by-value pass decremented without a
# matching arg-site inc, so two passes drove the element's refcount to zero
# while the container still held it. This fixture reads `src[0].clone()` and is
# named for the BARE `let s = v[i]` spelling (case (f)) that the typechecker no
# longer accepts -- `E_INDEX_MOVE_NON_COPY`, whose own remedy text names
# `v[i].clone()`. So it had been testing the unregistered path under the
# registered path's name.
#
# The lesson worth keeping is about this file rather than that fix. "No double
# free, no leak" was a property of the FIXTURE'S TWO PASSES, not of the defect:
# a third pass drives the count to -1 and frees the block twice, which glibc
# reports as `malloc(): unaligned tcache chunk detected`. A quarantine entry
# records what one program did on one leg -- it is not a characterization of the
# bug, and reading it as one costs the escalation.
#
# B-2026-09-07-55 REMOVED 2026-09-08, its owning row fixed. The entry read:
#
#   `__karac_rc_drop_E` frees a 120-byte block and reads it again — both ends
#   inside the same generated drop.
#   memory_sanitizer_tests::asan_shared_enum_boxed_struct_payload_moveout_no_double_free
#
# Both ends were in one drop because the leaf and the box held the SAME handle.
# `let tb = nd.then_block` off a by-value view of a shared enum's boxed payload
# aliased the box's `Option[shared]` child with no inc; the box's walk and the
# leaf's own value-drop then dec'd one ref, and the second dec read the freed
# block. The leaf now takes a ref of its own — the copy semantics
# `finish_owned_struct_destructure` already applied to the DESTRUCTURE spelling
# of the same move, which the field-access spelling never got.
#
# The 32 B leak at the same line is NOT this entry and is still open
# (B-2026-09-07-62): the walker frees no nested buffer even when the leaf is
# never moved out. Its cells measure identically before and after this fix,
# which is deliberate — copying the buffer here would strand the box's original
# and trade the use-after-free for that leak.
#
# B-2026-09-07-56 REMOVED 2026-09-08, its owning row fixed. The entry read:
#
#   `v[i] = <place>` releases the old element, then `main` reads through the
#   released 16-byte handle. Read is in `main`, not in a teardown helper.
#   memory_sanitizer_tests::asan_vec_plain_shared_index_overwrite_place_rhs_no_leak
#
# The read really was in `main`, and that is what made the entry misleading: it
# was read as "the index-assign lowering itself", and the index-assign turned
# out to be innocent. `let mut work = xs` over a by-value `Vec[shared T]` param
# deep-copies the buffer -- correctly, the caller keeps the original's drain --
# but the copy was a flat memcpy of RC HANDLES with no retain, so both
# containers drained the same boxes. Deleting the fixture's `work[0] = work[1]`
# line reproduces the identical read at the identical address.
#
# The lesson is the file's own, one row on: a quarantine entry records WHERE a
# report landed, which is not the same as where the defect is. `main` was the
# honest answer to "which frame read freed memory" and the wrong answer to
# "which lowering is wrong".
#
# B-2026-09-07-57 REMOVED 2026-09-08, its owning row fixed. BOTH its entries
# came off together. They read:
#
#   The one NON-heap finding: `stack-buffer-overflow`, a read at offset 40 of a
#   frame that has exactly one object.
#   memory_sanitizer_tests::asan_discarded_literal_projected_field_keeps_its_owner
#
#   The if/else sibling of the line above, and the same stack overread. It
#   reached this list under B-2026-09-07-43, whose LEAK it also had.
#   memory_sanitizer_tests::asan_discarded_literal_projected_field_if_else_read_after_declines
#
# No fix was written against either entry. The row was closed against
# `9ee19bbd2`, B-2026-09-07-48's fix, exactly as its own closing note said to:
# `lower_field_access_ptr` knew three receiver slot shapes and fell through to
# the raw slot pointer for a fourth, so a projected read off an RC-FALLBACK
# PROMOTED local GEP'd the 8-byte box HANDLE as if it were the struct. Both
# fixtures re-measured green on this leg after that fix, 1535 passed / 0 failed.
#
# THIS ENTRY IS THE COUNTER-EXAMPLE TO THE THREE LESSONS ABOVE, and it is worth
# keeping for that reason. B-2026-09-07-54, -55 and -56 each record a version of
# "a quarantine entry says WHERE the report landed, not where the defect is".
# This one said where the defect was. The frame layout WAS the localization:
#
#     This frame has 1 object(s):
#       [32, 40) 't' <== Memory access at offset 40 overflows this variable
#
# `t` is eight bytes because it holds a box handle rather than the 32-byte
# struct, and the read one word past it is precisely a GEP of field 1 computed
# against the handle's address. B-2026-09-07-48 had that as a written HYPOTHESIS
# and no way to test it; this leg turned it into a measurement. So the reading
# rule is neither "trust the entry" nor "distrust it" — it is that a report
# naming a STACK FRAME LAYOUT carries information a heap report does not, because
# the object's declared extent is in the message.
#
# The half ASAN could NOT see is the other half of the lesson. The same defect's
# `v.push(t.a)` spelling printed 0 against an oracle of 38 while running CLEAN
# under instrumentation — a wrong answer with every access in bounds. It was
# re-measured at 38 on all four surfaces before this removal. A fixture list
# gated on memory safety is silent about that class by construction, which is
# why the row's closing note asked for it to be checked separately.
#
# THE ACTIVE LIST IS NOW EMPTY. That is the ratchet arriving where it was aimed,
# not a reason to retire it: the leg still fails on any unlisted fixture that
# starts failing, and an empty list is the strongest form of that gate.

# The OTHER fixture stays, re-attributed below to B-2026-09-07-57 — it is a
# different defect that this row's leak was masking. Measured both ways: on the
# parent AND on the fix, `asan_discarded_literal_projected_field_if_else_read_-
# after_declines` fails this leg with `stack-buffer-overflow ... READ of size 8

#
# THE RATCHET CAUGHT THIS, which is the point of it running in both directions.
# The entry was removed on the strength of the `-O0` leg alone, where the fixture
# genuinely passes; this leg sees a strictly larger error class, so a removal
# justified by the smaller one is not justified here. Re-measure per leg before
# taking a line off either list.
#
# A discarded `if`/`else` reaches exactly one registrar
# (`try_track_discarded_user_drop_temp`), and `discard_branch_tail_aliases_a_temp`
# gated it by OR-ing `field_init_aliases_a_temp` across EVERY arm -- so one
# RC-boxed field projection declined the whole construct and whichever arm
# actually RAN lost its heap. The guard's premise, that the box goes on owning
# the projected field, was retired by `afe5abfbe`: the field loop now hands the
# literal an independent COPY, so the box owns the original and the literal owns
# the copy. Asking `rc_boxed_projection_mints_copy` -- the predicate `8f3751b15`
# added to the sibling registrar for the same question -- makes the branch
# spelling agree with the bare-statement one.
#
# The lesson worth keeping is about the QUARANTINE ENTRY, not the fix. Both
# fixtures take the PROJECTING arm, where the stranded buffer is the copy of
# `t.a` -- a dead allocation that `-O2` elides. That is the only reason this
# family looked `-O0`-only and landed on these lists at all. The same defect with
# the MINTING arm taken strands a live buffer at BOTH opt levels: 355 B in 5
# allocations, red under the plain `--features llvm` leg CI already runs, and now
# pinned by `asan_discarded_branch_projecting_arm_still_owns_every_path`. An
# `-O0`-only quarantine entry can be a fact about which arm the fixture happens
# to take rather than about the defect -- vary the path before believing the leg.
